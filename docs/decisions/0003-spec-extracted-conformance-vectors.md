# 0003 — conformance vectors are extracted from the spec

## Decision

Wire-format conformance vectors are generated by a Lean executable
(`lake exe vectors` in `spec/`) and committed under `contracts/vectors/`.
CI regenerates them and fails on any diff, so the committed file cannot
drift from the specification. The Rust test suite consumes the committed
file. The direction is one-way: Lean specifies, Rust conforms.

## Considered

- **Hand-written vectors.** They catch cross-implementation drift, but
  the vectors themselves are only as right as the hand that wrote them —
  when spec and vector disagree, nothing says which one is wrong.
- **Rust generates, Lean checks.** Inverts authority: the implementation
  would define the format and the spec would trail it. That ordering is
  how specifications rot into documentation.

## Why

The spec's `encode` is executable, so vectors derived from it are true
by construction against the model that carries the proofs (round-trip
`decode_encode` and whatever accumulates on top). Any implementation in
any language then has a single, proof-backed answer to "what are the
right bytes." Committing the generated file (rather than generating in
every consumer's build) keeps consumers toolchain-independent — the
Rust tests need no Lean — while the CI diff keeps the copy honest.

## What would reopen this

- Vector sets too large or too structured for a committed JSON file
  (e.g. randomized/property campaigns) — those would become a generated
  artifact with a pinned seed rather than a committed file.
- A second implementation language whose test harness needs a different
  vector format — extend the extractor, never fork the vectors.
