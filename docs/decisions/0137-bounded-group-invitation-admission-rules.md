# 0137 — bounded group invitation admission rules and revision numbering

> Clarifies 0093. Aligns `spec/Tacenta/Group.lean` with the code where it says so, and lists where it does not.

## Decision

**Revision numbering.** An invitation does not advance the roster revision. It
records the authority's current revision as its source revision, together with
the source roster digest, and travels to the target as a bootstrap control
(decision 0125). Only a roster successor advances the revision: an admission,
a removal or a closure. Adding a member therefore costs exactly one revision,
the admission. A group at revision 0 that invites one person and admits them
is at revision 1, and a second invitee admitted afterwards is at revision 2.
The Lean model previously recorded a successor for the invitation as well
(invite to revision 1, admit to revision 2); it is changed to the numbering
above and its traces read invite at revision 0, admit at revision 1.

**Creation.** `InvitationBook::create` refuses an invitation whose target
identity already appears in the active roster (which covers the exact member
and a second device of an existing identity) with `Conflict`, and refuses a new
invitation while the active roster already holds eight members with
`TooManyMembers`. An exact retry of an existing record returns that record
before the capacity check, so a retry never fails because the roster has since
filled. The pending invitations themselves do not count toward the eight.

**Admission.** `InvitationBook::admit` refuses a revision that is not strictly
greater than the invitation's source revision with `StaleSource`, because an
admission is a successor of the source roster or of a later one. A retry of an
admitted invitation at the same revision returns the record; a different
revision is a `Conflict`. The book has no roster to check, so the eight-member
cap and the one-device rule at admission are enforced where the successor
roster is built: `Roster::new` refuses a ninth member (`TooManyMembers`) and a
second device of an identity (`NonCanonical`).

**Acceptance is idempotent.** A repeated acceptance of an accepted-pending or
admitted invitation returns the committed record and changes nothing. The
acceptance control is retried up to three times and a crash may resend it, so
the second delivery must be safe. The Lean model's `accept?` refused a
repeat; it now returns the unchanged state for a repeat while the invitation
is unexpired or admitted.

**Model and code are tied by a vector.** `lake exe vectors group` prints a
trace of invite, accept, admit, revoke and refusal steps from the Lean model,
committed as `contracts/vectors/group-v1.json`; CI regenerates it with the
other four. `crates/tacenta-group/tests/model_vectors.rs` replays every step
against the Rust types and compares refusals and revision numbers.

## Where the Lean model and the code differ

`docs/claims.md` says the model "differs from the code where this record says
so". This is that list. It has three sources: the comment on the group trace
vectors in `spec/Vectors.lean` (items 1 to 3), a reading of `Group.lean` against
the Rust types (items 4 to 6) and a differential run of 18,000 random steps
generated by the model and replayed against the Rust types, which found the
rest and agreed on every step once items 1 to 3 were filtered out. A run of
random steps shows a difference when it finds one; it does not prove the list
complete.

1. **An exact retry of `create`.** The model refuses any invitation ID it already
   holds; the code returns the existing record for an exact retry (so a retry
   never fails because the roster has since filled). The trace vectors repeat an
   ID only with a different target, which both sides refuse.
2. **Revocation time.** The model's `revoke?` takes no logical time; the code's
   `revoke` takes `now` (it records an expired invitation as expired first).
3. **Removal of a non-member.** The model's `remove?` refuses a target that is
   not on the roster; the invitation book has no removal, so there is nothing to
   compare (removal is a roster successor, decided by the roster view).
4. **A repeat revoke and a repeat admit at the same revision.** The model
   refuses both (`revoke?` needs a pending or accepted invitation; a second
   `admit?` finds the target present); the code returns the record for each
   (retries of controls a crash may repeat).
5. **The last usable revision and the `Expired` status.** The model's
   `lastUsableRevision` and its "active" test are the only place it knows the
   reserved revision, and an expired invitation stays `pending` (expiry is a
   guard). The code refuses the reserved revision in `Roster::validate` and
   records an expired invitation as `Expired`.
6. **Closed groups.** The model refuses `invite?`, `accept?` and `revoke?` in a
   closed group (`active` is false). The code's `InvitationBook` does not look at
   the roster, so `create`, `accept` and `revoke` are not refused for that reason
   there; the coordinator refuses `invite` in a closed group (0141), and a
   receiver's terminal state (0139) refuses application traffic.
7. **The 33rd invitation.** The code refuses a new invitation record when the
   book holds 32; the model has no such cap (only the roster's eight).
8. **Roster growth without an invitation.** The code's `RosterView` accepts any
   well-formed successor from the authority, including one that adds a member
   nobody invited; the model adds a member only through `admit?`.
9. **A successor of a closed roster that changes its members.** The view refuses
   only a reopening; the model has no transition from closed to closed.
10. **Replay of an older control.** For a revision already in its history the
    model answers `duplicate` (same commitment) or `conflict`; the view answers
    `Duplicate` for the current revision only and `Rejected(StaleRevision)` for
    an older one, and the model folds stale and future into `staleOrFuture`
    where the view distinguishes `StaleRevision` and `MissingPredecessor`.
11. **What the model treats as opaque.** The source-roster digest, the canonical
    member order (0136), the byte layouts, the payload commitments and the
    core's commitment functions are not modelled; a commitment is a number.
12. **Whole mechanisms with no model counterpart.** The receiver (acceptance,
    dedup, the future window and queue, terminal state, event IDs), the outbox
    and its attempts, the control outbox, the final-attempt acceptance, recovery
    at an applied revision and the source-roster view (0135), redelivery (0144),
    held roster controls (0142) and the coordinator's fence and latch (0134,
    0143). Nothing here is claimed to be modelled.

**What the vector replay checks.** `crates/tacenta-group/tests/model_vectors.rs`
compares, per step, whether it was accepted, the revision, the sorted roster
members and, per invitation, its target, source revision and status. It does not
compare expiry times, digests, the closed flag or the kind of a refusal. Of 29
single-change mutants of the Rust types, the replay kills 15, and only one of
those (a merely pending invitation being admissible) is killed by the vector
alone; twelve are killed only by other tests and two survive every product test
(the observed digest being ignored in `accept`, and a repeat revoke becoming an
error, which agrees with the model and differs from the code). Of 16 mutants of
the model, five die at `lake build`, ten at the CI diff and the Rust replay, and
one (the `>=` in the expiry test of `invite?`) survives everything. The vector,
the model and its theorems have had no human review.

## Considered

- Make the code follow the model: an invitation consumes a revision. That
  spends a revision, and a control fan-out to every member, on an invitation
  that may be revoked or expire; it changes the live traces and the wire bytes
  the client tests already fix (admission at revision 1).
- Keep two numberings and document the difference. That leaves a model whose
  traces mean something other than the code.
- Make acceptance strict, as the model had it. A resent acceptance would then
  fail at the authority.

## The five questions

This record is in a product crate (`tacenta-group`) and touches no
`tacenta-core` behaviour. The trusted core is unchanged; the record's bytes and
rules are product-owned and covered by this repository's tests; it does not move
protocol functionality into the core.

## Why

The revision space is bounded (`u64::MAX` is reserved) and every revision is a
control message that every member must accept in order. Revisions should count
changes to who is in the group. An invitation is authority-side state plus a
point-to-point bootstrap, so the model follows the code and the design notes
for this profile ("B is admitted at r1 ... C observes r1 pending, then is
admitted at r2"; those notes are not in this repository, and the rule stands on
the reasoning here).
Retry safety decides the acceptance question: an operation that a crash can
repeat must not turn its own repeat into an error.

## What would reopen this

A profile in which an invitation is itself a group-visible event (a delegated
authority, or a group that shows pending invitations to every member) needs a
revision for it. A multi-device profile changes the second-device rule.
